# claude-ds — Shared Design-System Governance & Scaffold CLI

## Problem Statement

Collin runs multiple UI projects (and increasingly some non-UI projects) inside `~/Claude Projects/`. Every project currently invents its own conventions for how Claude Code should be allowed to touch design-system code: which hooks fire, what the contracts say, where atoms vs. composites live, how tokens are enforced, how exceptions get logged. The result is drift — the rules that exist in one project don't exist in the next, projects built before the conventions stabilized are full of ad-hoc patterns, and there is no mechanical way to roll a tightened rule out to every repo that should have it. The detailed scaffold described in `design-system-scaffold.md` (hooks, skills, contracts, tier A/B model, manifest-as-generated, failure-log promotion workflow) only exists as a document; nothing installs it, nothing keeps projects in sync with it, and nothing helps an existing repo adopt it without manually copying files and breaking what's already there.

## Solution

`claude-ds` is a small CLI distributed from a private GitHub repo and invoked via `npx github:collod873/claude-ds#vX.Y.Z`. It owns two things: (1) a stack-agnostic **universal core** of governance contracts — hook output format, exit-code conventions, the shared `log-failure.sh` helper, the tier A/B model, the manifest-is-generated principle, the `contracts.md` / `exceptions.json` / `failure-log.md` workflow, the commit convention, and the precedence rule — and (2) one or more **stack packs** that supply the concrete hook scripts, showcase generator, directory layout, and file-extension specifics for a given stack. A project declares its pack in `.claude-ds.json` and the CLI knows which files it owns there.

Adoption splits cleanly into two paths. The greenfield path is a single command, `init`, which bootstraps a fresh project with the full scaffold. The brownfield path is a four-stage ladder of explicit subcommands: `audit` (read-only diff and cleanup suggestions), `adopt` (installs governance and an empty scaffold with rules in WARN mode), `migrate <path>` (moves one existing component into the scaffold shape and registers an `exceptions.json` entry where it can't yet fully conform), and `enforce` (flips rules from WARN to BLOCK once the exception count is acceptable). A sixth subcommand, `sync`, is the steady-state update path for both paths once installed: it fetches the latest pinned tag, diffs the upstream against what the local project has, and applies changes only to files the CLI owns. The CLI never deletes user content and never edits files outside its declared ownership. Files that are partly CLI-owned and partly user-owned (root `CLAUDE.md`, `.claude/settings.json`, `package.json`) are managed via marker-block regions: the CLI only touches content between `# >>> claude-ds managed >>>` and `# <<< claude-ds managed <<<` markers; if a user edits inside a managed block, `sync` warns and aborts that file rather than clobbering.

Version pinning is per-project and explicit: `.claude-ds.json` records the scaffold version and selected pack; `sync` never auto-updates and always shows a confirmable diff before applying. v1 ships the `next-react` pack; future packs (Vite, Remix, generic-governance-only) are pack-only releases that don't disturb existing projects.

## User Stories

1. As Collin starting a new UI project, I want to run one command and get a fully configured `.claude/` directory, design-system skeleton, hooks in WARN mode, and a populated `.claude-ds.json`, so that I never re-create governance scaffolding by hand.
2. As Collin adding `claude-ds` to an existing ad-hoc project, I want to first run a read-only audit that shows me what's already there, what conflicts with the scaffold, and what cleanup it recommends, so that I can decide whether to adopt before anything changes on disk.
3. As Collin adopting `claude-ds` into an existing project, I want the install to leave my existing components in place and only add the scaffold next to them with rules in WARN mode, so that nothing I've built breaks the moment I install.
4. As Collin migrating one existing component into the scaffold, I want a single `migrate` invocation to move the file into the right tier directory, generate the companion `.showcase.tsx` / `.states.json` / `.snapshot.png` stubs, and register a time-boxed `exceptions.json` entry for whatever it can't yet conform to, so that I make progress incrementally instead of all at once.
5. As Collin flipping a project from WARN to BLOCK enforcement, I want a single `enforce` command that refuses to run unless the exception count is below a configured threshold, so that I can't lock down a project that's not actually ready.
6. As Collin updating a project to a newer scaffold version, I want `sync` to fetch the latest pinned tag, show me exactly which managed files would change and which marker-blocks would be rewritten, and apply nothing until I confirm, so that scaffold updates can never silently break a downstream project.
7. As Collin tightening a rule in the universal core, I want to publish one new tag of `claude-ds` and have every consuming project pick up the new rule the next time it runs `sync`, regardless of which stack pack it uses, so that I never have to manually propagate a rule change across N repos.
8. As Collin adding a new stack pack later (e.g. `vite-react`), I want to ship it as a new git tag whose contents leave the existing `next-react` pack files unchanged, so that projects pinned to the previous tag remain bit-identical until they explicitly `sync`, and projects that later upgrade only see file changes inside their declared pack plus the universal core — never inside packs they don't use.

## Implementation Decisions

**Architecture — two layers, one repo.** The CLI source lives in a single private GitHub repo, `collod873/claude-ds`. Inside it, there are two top-level concerns: the **universal core** and a directory of **stack packs**. The core defines stack-agnostic contracts: the hook input/output format (`<file>:<line>: <rule-id>: <fix-hint>` on stderr; exit `0` allow, `2` block, `1` reserved for hook self-error), the `log-failure.sh` interface every blocking hook must call through, the `contracts.md` outline (principles → atom rules → composite rules → tier boundaries → typography/motion/icons sections), the `exceptions.json` schema (rule-id, file, reason, expiry), the `failure-log.md` append format, the manifest-is-generated principle, the precedence rule (hooks > contracts > principles > skills), and the commit convention (`type(scope): subject`). Each pack supplies concrete implementations of: the hook scripts that satisfy the core contract, a `showcase` generator for the pack's framework, the canonical directory layout for that pack, the per-file extensions and globs the hooks match against, and the linter/test commands the pack uses. Packs do not redefine the core contracts; they implement them.

**Pack declaration and project config.** Every consuming project carries a single config file (`.claude-ds.json`) at its repo root. The file is fully user-owned (not hybrid, not managed) — the CLI reads it and validates its schema on every invocation but never rewrites it except as the explicit effect of `init`, `adopt`, `enforce`, or `sync` (the file's content is the user's record of how they want the CLI to behave). Schema (v1, locked):

- `version` (string, required) — pinned scaffold git tag, e.g. `"v1.4.0"`.
- `pack` (string, required) — selected pack name, e.g. `"next-react"`.
- `mode` (string enum, required) — `"warn"` or `"block"`. `init` defaults to `block`; `adopt` defaults to `warn`.
- `enforce_threshold` (integer, optional, default `10`) — maximum allowed exception count for `enforce` to flip WARN → BLOCK.
- `removed` (array of strings, optional, default `[]`) — paths of managed files the user has rejected re-creation for; `sync` skips re-installing any path in this list.

Any field outside this schema is a validation error. The CLI never adds keys to `.claude-ds.json`; the user adds optional keys themselves.

**File ownership categories.** Every file the CLI knows about belongs to exactly one category, declared in a manifest inside the pack. *Managed* files are owned by the CLI; `sync` overwrites them freely (hook scripts, the shared `log-failure.sh`, the `scripts/` directory contents, anything under `.claude/hooks/`). *Seeded* files are created on `init`/`adopt` and never touched again by the CLI (the project's `contracts.md`, `tokens.json`, design-system `README.md`, `package.json`, `commitlint.config.js`). *Generated* files are never authored by the CLI at all (`manifest.json`, `*.snapshot.png` — those are produced by the project's own post-write hook). *Hybrid* files are partly CLI-owned. At v1, hybrid files are root `CLAUDE.md` (markdown marker-block format) and `.claude/settings.json` (JSON owned-keypath format).

The v1 hybrid set is deliberately minimal. `.claude/settings.json` is a **hybrid+json** file: the CLI applies namespace-aware merge semantics to the `hooks` top-level key; all other keys (`permissions`, `env`, etc.) are user-owned and preserved across `sync` and `adopt`. On `sync`, the CLI merges only the `hooks` key from upstream into the on-disk file; if the merged result is identical to the current file the file is skipped, otherwise it is rewritten. On `adopt`, if `.claude/settings.json` already exists, the CLI merges `hooks` from the pack content into the existing file; if absent, the pack content is written as-is. The `--backup-settings` flag on `adopt` no longer exists; no backup is needed because user-owned keys are never overwritten. `package.json` is seeded on `init`/`adopt`; the CLI never edits scripts inside an existing `package.json`.

**Hook namespace rule (v0.1.3+).** Within the `hooks` object, ownership is determined at the individual hook-entry level, not at the event-key level. claude-ds owns only hook entries whose `command` field starts with `.claude/hooks/` — the pack's hook installation directory. All other hook entries (user-defined validators, banner scripts, external tooling) are user-owned and survive every `sync` and `adopt` unchanged. The merge algorithm: (1) deep-clone `current.hooks` as the base; (2) strip any claude-ds-owned entries (command starts with `.claude/hooks/`) from the base so stale pack hooks don't accumulate; (3) for each event in `upstream.hooks`, if a matcher block with the same `matcher` string already exists in the base, append upstream's inner hooks (deduplicating by command); otherwise append the whole matcher block; if the event key doesn't exist in the base, create it. This means a user can have `PreToolUse` validators, `SessionStart` banners, or their own `PostToolUse` entries and none of them will be touched by claude-ds — only entries under `.claude/hooks/` are ever added, replaced, or removed.

**Marker-block protocol (text files).** Hybrid text files use line-based markers — for markdown the exact strings are `<!-- >>> claude-ds managed >>> -->` and `<!-- <<< claude-ds managed <<< -->`; for shell-comment files (`.sh`, `.bashrc`-style) the strings are `# >>> claude-ds managed >>>` and `# <<< claude-ds managed <<<`. On `sync`, the CLI parses each hybrid file, locates the marker pair, computes the desired content from the upstream pack version, and replaces only the content between markers. Before writing, the CLI compares the current in-marker content against what the *previously installed* version would have produced (using the cached upstream snapshot from the previously-pinned tag); if they differ, the user has edited inside the managed block, and `sync` aborts that file with a warning, leaving the rest of the sync to proceed. Missing closing marker, multiple marker pairs, or nested markers are all parse errors that abort the file.

**Subcommands.** The CLI exposes exactly these top-level commands at v1: `init` (greenfield bootstrap — creates the full scaffold; refuses if `.claude-ds.json` already exists), `audit` (read-only diff and cleanup report; mutates nothing), `audit --suggest-removals` (audit plus a list of ad-hoc files the scaffold would recommend deleting; still mutates nothing), `adopt` (brownfield install — drops in `.claude/` and the empty `design-system/` skeleton in WARN mode; writes `.claude-ds.json`; refuses if one already exists), `migrate <path>` (move one component into the scaffold and register exceptions), `enforce` (flip WARN → BLOCK; refuses if exception count is above the configured threshold), `sync` (update to the latest pinned tag; shows diff and confirms before applying), and `version` (print installed-in-this-project version + latest available tag).

**Versioning.** Single-repo, single-tag releases. Every scaffold release is one git tag (`v1.4.0`); the tag's contents include the universal core and every shipped pack at that point in time. `.claude-ds.json` pins one `version` string. There is no separate core-version vs. pack-version pin at v1. (A future iteration may introduce independent pack versioning if it becomes painful; v1 explicitly avoids that complexity.) `sync` discovers updates by listing the upstream tags (`git ls-remote --tags`) and comparing against the pinned `version`; updates are never automatic.

**CLI language and packaging.** TypeScript source under `src/`; build emits `dist/cli.js` which is referenced as the package `bin`. The compiled `dist/` is committed to the repo so `npx github:...` works without requiring the consumer to build. No npm publish step; releases are git tags only.

**Brownfield WARN mode.** When `adopt` installs in an existing project, every rule defined by the pack is installed in WARN mode by default. WARN mode means: hooks still run, violations still log to `failure-log.md` with full context, but no hook exits with code `2`. Violations are visible (the project owner can see what would block under enforcement) without disrupting work. `enforce` is the explicit transition from WARN to BLOCK, gated on exception count.

**`migrate` collision and tier classification.** When `migrate <path>` is invoked, the CLI determines the target tier (atom vs. composite) by a deliberately shallow check: a regex scan of the source file's `import` statements. If the file imports from `design-system/atoms/*`, it is a composite candidate; if it imports nothing from `design-system/*`, it is an atom candidate; if it imports from `design-system/composites/*`, that is a tier violation and `migrate` aborts with a clear error. The user can bypass classification entirely with `--tier atom|composite`. No AST parsing at v1 — the regex approach is intentional for simplicity; AST is a v2 concern if false-positives become real. If a target with the same name already exists in the destination, the CLI errors and refuses to overwrite (the user must resolve manually or pass `--rename <new-name>`). Conformance issues that can't be auto-fixed (data opinion baked into the component, non-token color values) are registered in `exceptions.json` with the corresponding rule ID, the file path, a reason supplied by the user via prompt (or `--reason` flag), and an expiry date defaulting to 90 days out.

## Testing Decisions

A good test in this CLI is one that drives a real filesystem from a known starting state and asserts on the resulting tree, the exit code, and the stdout/stderr of the invocation. Vitest runs these as integration tests against temporary directories created per-test; no mocks for the filesystem itself. The CLI's pure logic (marker-block parse, exception-count gate, version comparison, hybrid-file merge) is also unit-tested with synthetic inputs.

**What gets tested.** Every subcommand (`init`, `audit`, `audit --suggest-removals`, `adopt`, `migrate`, `enforce`, `sync`, `version`) has at least one happy-path integration test and one refusal-path test (preconditions violated, conflicts detected, etc.). The marker-block parser and merger are unit-tested across the file formats they support (markdown, json, package.json scripts block). The `sync` diff algorithm is unit-tested with synthetic before/after pack states. The `migrate` collision logic is integration-tested with a real conflicting file.

**Pack-internal test fixtures.** Each pack ships its own test fixtures inside the `claude-ds` repo (e.g. `packs/next-react/tests/fixtures/` plus a `packs/next-react/tests/*.test.ts` runner). The fixtures are minimal fake project trees and the runner invokes the pack's actual hook scripts against those trees, asserting on exit code and stderr per the universal hook contract. Vitest runs these as part of `claude-ds`'s overall test suite — pack hook correctness is `claude-ds`'s responsibility, verified by fixture, not by depending on a real consuming project. What is *not* tested at v1: the pack's interaction with a real Claude Code session (i.e. the hook actually firing because Claude Code triggered it on a Write tool call). That end-to-end loop is smoke-tested manually on the first real consumer of v1.

**Prior art.** chezmoi's marker-block managed-region model; `oh-my-zsh`'s upgrade flow; `create-next-app` for greenfield bootstrap shape; `eslint --init` for the WARN-vs-error mental model.

## Data Model

N/A — `claude-ds` is a CLI with no persistent backend state of its own. The only files it reads or writes are (a) the consuming project's `.claude-ds.json` configuration file, (b) project files inside its declared ownership categories, and (c) `exceptions.json` and `failure-log.md` inside the consuming project. Schemas for those three files are described in Implementation Decisions; there is no database, no remote API, no server-side state.

## Business Rules

- **Universal contracts are versioned with packs in v1.** A single git tag of `claude-ds` is the unit of release; there is no separate core-version vs. pack-version. This is a deliberate simplification at v1 and may be revisited if it becomes painful.
- **The CLI never deletes user content.** `audit --suggest-removals` may *recommend* removals, but no subcommand removes files without explicit human approval and an explicit invocation that names the file. Automated cleanup of "ad-hoc" code does not exist.
- **`sync` never auto-updates.** Every sync run shows a diff and waits for confirmation. There is no quiet mode, no `--yes` flag at v1.
- **Marker-block tampering is non-destructive.** If a user has edited inside a managed marker block, `sync` aborts that file with a warning and continues with the rest of the sync; it does not overwrite user edits.
- **v1 gap — fully-managed hand-edit detection.** Detecting hand-edits to fully-managed files (outside marker blocks) requires comparing the on-disk file against a prior-tag snapshot, which v1 does not cache. At v1, `sync` treats every managed file as "upstream wins." The hybrid marker-region guard (text files) and hybrid+json owned-keypath merge (`.claude/settings.json`) are unaffected — those mechanisms preserve user-owned content by design. Closing the fully-managed hand-edit gap requires a snapshot cache (`.claude-ds/snapshots/`) populated at `init`/`adopt`/`migrate`/`sync` time; deferred post-v0.1.0.
- **`adopt` is brownfield-safe.** It refuses to run if `.claude-ds.json` already exists. It installs every rule in WARN mode; it never moves or rewrites existing components. Component migration is exclusively `migrate`'s job.
- **`enforce` is gated on exception count.** WARN-to-BLOCK transitions require the project's `exceptions.json` to have fewer entries than the configured threshold (default: ≤ 10, configurable per-project in `.claude-ds.json`). The threshold prevents projects from flipping to BLOCK with hundreds of unresolved violations.
- **Pack version compatibility.** A project pinned at scaffold v1.X.Y must be able to run `sync` against scaffold v1.X+N.Z without breaking. Backward-incompatible changes within a major version are forbidden by policy; if a change is incompatible, the major version bumps and `sync` to the new major requires an explicit `--major` flag.
- **Precedence on conflict.** When the project's own rules disagree with the pack's rules, the pack wins (hooks > contracts > principles > skills, as defined in the source scaffold doc). Projects cannot silently override pack rules; they must use `exceptions.json` with a reason.

## Views

N/A — `claude-ds` is a CLI; it has no GUI. Its user-facing surface is exactly: command-line argument parsing, stdout reports (audit diff, sync preview, version), stderr error messages, and one-line interactive confirmation prompts before destructive actions.

## Edge Cases

- **Consumer runs `sync` while offline / GitHub unreachable.** The CLI surfaces a clear error and exits non-zero without modifying any files. No partial sync, no fallback to a cached older tag.
- **Pinned tag no longer exists upstream.** `sync` reports the missing tag and refuses to proceed. The user must either downgrade their pin or update it to a current tag.
- **`.claude-ds.json` is malformed or hand-edited into an invalid state.** Every subcommand validates the config on startup and prints a precise schema error before doing anything else.
- **Marker block exists but is malformed (missing closing marker, nested markers).** `sync` and `adopt` both detect this on file parse and abort the affected file with a clear error; the rest of the sync continues.
- **A managed file has been deleted by the user since last `adopt` or `sync`.** `sync` treats the absence as a request to re-create the file; the file is re-installed and a notice is printed. The user can prevent re-creation by adding the path to a `removed:` list inside `.claude-ds.json` (which is itself a marker-block-free user-owned section).
- **Stack pack referenced in `.claude-ds.json` does not exist at the pinned tag.** Every subcommand validates pack presence on startup; an unknown pack name aborts with a clear error.
- **`migrate <path>` is invoked on a file outside the project root, or on a directory, or on a non-component file.** The CLI validates the target and refuses with a clear error before any move occurs.
- **`enforce` is invoked when no `claude-ds` install has happened (`.claude-ds.json` absent).** Refuses with a precise error pointing at `adopt` or `init`.
- **Multiple `claude-ds` invocations race against each other.** v1 does not lock; the assumption is single-user, single-machine, sequential invocations. If concurrent invocations become a real problem, a lockfile is a v2 concern.
- **A consuming project has its own pre-existing `.claude/settings.json`.** `.claude/settings.json` is hybrid+json at v1; `adopt` merges the pack's `hooks` key into the existing file, leaving all other keys (`permissions`, `env`, etc.) untouched. No backup is needed and no `--backup-settings` flag exists. If the file is absent, the pack content is written as-is.
- **The `next-react` pack version changes which files are managed vs. seeded.** A file that was seeded in version N but becomes managed in version N+1 is treated as managed from version N+1 onward; `sync` will rewrite it on the next run. The release notes for the pack must call out any such transition.

## Integrations

- **GitHub (private repo).** `claude-ds` lives at `github.com/collod873/claude-ds`. Consumers invoke `npx github:collod873/claude-ds#vX.Y.Z`. Private-repo access requires the consumer to be authenticated (existing `gh` auth or a PAT). The CLI itself does not authenticate; it relies on the consumer's existing GitHub credentials.
- **`npx` / Node.js.** The CLI runs under Node 20+ (LTS) and is invoked via `npx` against a git ref. No npm registry publishing.
- **Claude Code hooks.** The pack ships hook scripts that the CLI installs into `.claude/hooks/`. Claude Code itself executes these — `claude-ds` is not in the runtime path during hook execution, only during install and sync.
- **Claude Code settings.json.** `init` and `adopt` install `.claude/settings.json` as a fully CLI-managed file (refusing to overwrite a pre-existing one without an explicit backup). It contains the pack's required Bash denies and hook registrations. Project-specific permissions or hooks the user wants to add go in `.claude/settings.local.json`, which Claude Code natively merges and which `claude-ds` never reads or writes.
- **Git (project-side).** The CLI does not commit on the consumer's behalf at v1. After `adopt`, `migrate`, or `enforce`, the user is reminded to commit; the CLI prints a suggested commit message. No automated commits.
- **Adapters / planning-system / Knowledge-Base.** Out of scope for v1. `claude-ds` does not write to or read from `Knowledge-Base/wiki/` or planning-system adapters. (Future packs may register skills that interact with these, but the CLI's install logic does not.)

## Out of Scope

- **Multi-stack packs at v1.** Only `next-react` ships. Vite, Remix, and generic-governance-only packs are explicit future work.
- **Shared component code.** `claude-ds` does not ship a component library. Atoms and composites are per-project; only the directory shape, hook rules, and contracts are shared.
- **Independent core vs. pack versioning.** v1 ships single-tag releases. Decoupled versioning is a later concern only if real pain materializes.
- **Telemetry, analytics, usage reporting.** None. The CLI does not phone home.
- **`sync` auto-apply / `--yes` flag.** Every sync requires confirmation at v1.
- **Concurrency / locking.** Single-user assumption at v1.
- **Migration assistance for non-component files** (e.g. moving an existing `lib/` utility into `design-system/utils/`). `migrate` at v1 only handles component-shaped files (`.tsx` with an associated render).
- **A web UI or dashboard view of project conformance across repos.** Audit is per-repo, terminal-only. A multi-repo conformance dashboard is a separate future product.
- **Auto-generated PRs for `sync` updates.** v1 prints the diff locally; the user runs git themselves.

## Further Notes

- The CLI name `claude-ds` was chosen deliberately to signal Claude-Code-coupled. Hooks, skills, and `settings.json` registration are all Claude Code concepts; this tool is not pretending to be stack-agnostic governance for arbitrary build pipelines. If a project doesn't use Claude Code, it doesn't need `claude-ds`.
- The grilling transcript that produced this spec is preserved in this session's history and reproduced near-verbatim in the Decisions Resolved block presented before approval. The `audit` → `adopt` → `migrate` → `enforce` ladder is the load-bearing UX commitment of the project; if implementation pressure tries to collapse those four into fewer commands, that's a spec-rewrite event, not a plan-level shortcut.
- The `next-react` pack's *content* (which specific hook scripts ship, the directory layout, the showcase generator shape, the `contracts.md` outline, the `scripts/` inventory) is described comprehensively in `design-system-scaffold.md` in the `~/Claude Projects/General/` workspace. The two documents have non-overlapping authorities: **this spec is authoritative for `claude-ds` itself** — CLI behavior, install logic, file ownership categories, marker-block protocol, versioning model, subcommand surface. **The scaffold doc is authoritative for `next-react` pack content** — which hooks exist, what they enforce, what the directory tree looks like. The CLI's responsibility is to install whatever the pack's manifest declares; it does not encode pack-specific knowledge. If the two documents disagree on something that falls on this spec's side of the line (CLI behavior), the spec wins; if they disagree on something that falls on the scaffold doc's side (pack content), the scaffold doc wins. Pack content is locked into v1 via a snapshot taken at the time of the v1 release — once tagged, the pack's content is fixed for that tag.
- The decision to write the CLI in TypeScript with a committed `dist/` is partly about hooking into the existing `npx github:org/repo#tag` install pattern with no extra build step on the consumer, and partly so that pack manifests (which describe file ownership categories) can be typed and validated at build time on the scaffold side.
- Token cost is not a constraint per Collin's standing preference; quality and coherence are. The spec is verbose where it needs to be (file ownership categories, marker-block protocol, edge cases) because those are where install-CLIs typically fail in practice.

## Acceptance Criteria

- `packs/next-react/` must declare every file enumerated in `design-system-scaffold.md`. The next tag must not ship with the manifest missing any scaffold-declared file.
